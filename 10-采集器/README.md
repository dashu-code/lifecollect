# lifecollect —— 数字生命档案采集器

## 这是干什么的

把散落在微信、笔记、照片、邮件里的材料，收拢成**一套不依赖任何软件、二十年后仍然能读的档案**。

## 为什么需要它

现有工具都从"材料已经整理好了"这一步开始。而现实中，所有人卡在第一步：

- 材料散在多个 App 里，导不出来，或者导出来是一堆格式各异的文件
- 材料**单向衰减**——人在世时可采，人走之后账号被回收、手机被重置、记录被删
- 原始素材里**没有**"这条是闲聊、那条是观点"的信息，而下游的模型训练需要它

所以这个工具站在所有下游工具的上游，只做两件事：**采集**和**标注**。
它不训练模型、不克隆声音、不生成任何合成内容——那些是后面的事，且是用户的决定。

## 做完得到什么

一个文件夹。用文件管理器打开，用记事本就能看：

```
档案/
├── 00-说明.md          ← 永远明文。告诉十年后的读者这是什么、谁能用
├── 01-授权/            ← 授权声明、身后指令、密钥托管。任何使用者必须先读
├── 10-原始/            ← 原始素材。永不修改、永不删除。这是唯一的权威
├── 20-派生/            ← 从原始素材派生的可读记录。坏了能重新生成
├── 30-索引/            ← SQLite 检索库。整个删掉也不影响档案完整性
├── 40-呈现/            ← 总览、会话清单、高价值样本、待处理问题
└── 90-审计/            ← 操作日志，只追加
```

**权威性在文件上，不在数据库上。** 这是整个设计的核心。生成它的软件哪天不存在了，
档案依然是完整的。

## 怎么用

```powershell
# 0. 前置：Python 3.11+，装唯一一个依赖
pip install -r requirements.txt
Set-Location "10-采集器"

# 1. 初始化档案（standard 会要求设口令）
python -m lifecollect init --root "D:\档案" --security-level standard --subject "张三"

# 2. 看看三个安全级别分别挡什么、不挡什么
python -m lifecollect levels

# 3. 导入材料（--self 是你在导出文件里的昵称，必须给对）
python -m lifecollect import --root "D:\档案" --source wechat --self "我" 聊天记录.csv
python -m lifecollect import --root "D:\档案" --source documents --self "我" 随笔.txt
python -m lifecollect import --root "D:\档案" --source wechat 语音目录

# 4. 标注 → 建索引 → 出清单（顺序不能反：标注会改写记录，索引从记录重建）
python -m lifecollect tag   --root "D:\档案"
python -m lifecollect index --root "D:\档案"
python -m lifecollect view  --root "D:\档案"

# 5. 查看
python -m lifecollect stats  --root "D:\档案"
python -m lifecollect search --root "D:\档案" 成本 --self-only

# 6. 加密（把所有含内容的文件锁起来）
python -m lifecollect lock   --root "D:\档案"
python -m lifecollect status --root "D:\档案"     # 不需要口令
python -m lifecollect verify --root "D:\档案"     # 校验密文能解开

# 7. 解锁（读之前要解，解完密文默认保留）
python -m lifecollect unlock --root "D:\档案"
```

不传 `--self` 也能导入，但所有消息的方向会标成 `unknown`——这是有意的：
**"不知道是谁"和"知道是对方"是两回事**，猜错会让下游把陌生人的话当成档案主人的。

## 桌面界面

有两种跑法：

```powershell
# A. 原生窗口（pywebview，需要 WebView2；Win11 已预装）
python -m lifecollect.ui --root "D:\档案"

# B. 只起本地 HTTP，自己用浏览器打开
python -m lifecollect.ui --root "D:\档案" --no-window --port 8765
# 然后访问 http://127.0.0.1:8765/
```

**先看效果再建真档案**：仓库里有一个现成的演示档案（合成数据，可直接删）

```powershell
python demo_ui.py
python -m lifecollect.ui --root "_demo_ui\档案"
```

演示档案的口令是 `demo-password-123`（只在演示数据上用）。

**打开先是一份手册，不是仪表盘。** 第一次打开看到的是七章向导，
一章一章讲清楚「这是什么 → 为什么 → 怎么做 → 做完能看到什么」。
数据在你走完流程之后才出现，不预先塞满编造的示例。

手册章节：

| 章 | 主题 |
|---|---|
| 1 | 这是什么 — 它不是什么，为什么需要它 |
| 2 | 建立一个档案 — 安全级别怎么选（可直接在界面里建） |
| 3 | 导入材料 — 材料分级、两个陷阱、具体命令 |
| 4 | 标注 — 七种类型和「宁可说不知道」的设计 |
| 5 | 检索 — 中文分词为什么麻烦、行为边界 |
| 6 | 呈现 — 四份清单，重点是主动列毛病的那份 |
| 7 | 加密 — 三个级别、永远明文的设计、代价 |

工作台有六个页面：概览（含档案结构图和三个级别并排对比）、记录（按类型/谁说的筛选）、
检索（中文子串 + 高亮）、呈现（四份清单）、授权（声明/身后指令/密钥托管）、
加密（锁定状态 + 加锁/解锁/校验）。每个页面在没有数据时显示空状态并指回手册，
不是报错，也不是假数据。

**界面设计**：瑞士风格 / 构成主义。严格网格、细线、单色加一点朱红、
大字与极小字的对比、大量留白。没有圆角、没有阴影、没有渐变。

**UI 的安全边界**：

- 只绑 `127.0.0.1`，端口随机
- **给了口令就只验证口令，不许用 DPAPI 绕过**（否则本机输任意口令都能解锁）
- 锁定后，记录/检索/呈现接口一律拒绝；授权页永远可读（它本来就是明文的）
- UI 不接触原始数据源，采集流程仍然是 CLI 的活

## 设计约束（都是实测踩出来的，不是理论）

| 约束 | 来源 |
|---|---|
| **所有文本 IO 显式 `encoding="utf-8"`** | 中文 Windows 的 Python stdout 默认 GBK。DLRS 项目自己就栽在这 |
| **内部路径一律正斜杠** | DLRS 的 6 条管线在 Windows 上全废，因为用斜杠前缀校验反斜杠路径 |
| **中文检索必须自己做字符级索引** | 实测：`unicode61` 把整句当一个 token（`关键是成本`）；`trigram` 只建 3 字滑窗，双字词全废。见 `store.py` 里的注释 |
| **索引和查询两侧都要 NFKC 归一化** | 全角字母 `Ａ` 的 `isalnum()` 为 `True`，会走拉丁分支。不归一化的话索引里是全角小写 `ａ`、用户敲的是半角 `A`，永远对不上 |
| **丢弃非打印字符** | `\x00` 既不是 alnum 也不在 CJK 范围，不丢会被原样拼进 FTS5 查询串，把引号搞成未闭合直接抛错 |
| **输入一律加引号做字面匹配** | 用户输入的 `* " OR NEAR - ^ ()` 全部被中和。本工具是子串搜索，不是查询语言 |
| **不假设时间** | 抠不出时间就写 `None`，在统计里单列。不拿导入时间冒充消息时间 |
| **索引层必须可抛弃** | 重建走临时库 + 原子替换，重建失败不破坏已有索引 |
| **授权文件永远明文** | 否则会做出一个没人知道是什么、也没人知道谁能用的加密包——比不加密更糟 |
| **只追加，不修改原始层** | 原始层被改写，档案的可信度就永久受损 |

### 中文检索的行为边界（有意设计，不是缺陷）

短语匹配**要求字符连续**：

- 搜 `成本` → 命中"关键是**成本**"
- 搜 `拍照`，语料是"**拍**了几张**照**片" → **不命中**（中间隔着字）
- 搜 `照` → 命中（单字）

这个"严格"是有意的。若改成松散匹配（字符都出现就算），
`本成` 也会命中 `成本`，误报会多到没法用。
**宁可漏，不可错**——漏了换个词就能找到，错了用户会以为数据里真有那句话。

### 已知限制（未解决）

| 限制 | 影响 |
|---|---|
| 会话标题 / 文件名不进索引 | 搜文件名搜不到，只能搜消息内容 |
| 语音消息内容不可检索 | 需要 ASR，未实现 |
| 标点会被丢弃 | 搜 `成本，` 等同搜 `成本`，无法精确匹配标点 |
| 拉丁词按整词匹配 | 搜 `cost` 不命中 `costly`（中文侧是子串匹配，两侧行为不同） |

## 安全级别的立场

三个级别由**用户选**，但选择界面必须同时显示"挡什么"和"**不挡什么**"。

一个说不出自己保护边界的加密开关，比没有加密更危险——用户会以为它保护了
它没保护的东西。所以 `paranoid` 级别会明确告诉用户：
**密钥丢失即永久不可读，没有任何人（包括作者）能恢复。**

## 加密是怎么做的

### 三个级别

| 级别 | 密钥保护 | 实现 |
|---|---|---|
| `basic` | 无 | 不加密。没有任何密钥 |
| `standard` | DPAPI + 口令 | 主密钥被 Windows DPAPI 包裹（本机免密），**同时**被口令包裹（换机器可恢复） |
| `paranoid` | 仅口令 | 不落 DPAPI。每次解锁都要输口令 |

**为什么 standard 也要口令方式**：只靠 DPAPI 的话，Windows 账户一旦重建
（换主板、重装系统、账户迁移），密钥就永久取不回来了。DPAPI 是便利性，
不是保险。真正保证"换了设备还能打开"的是口令 + 文件里保存的 KDF 参数。

### 密码学选择

| 项 | 选择 | 理由 |
|---|---|---|
| 对称加密 | **AES-256-GCM** | 认证加密。密文改一个字节，解密必须失败 |
| 密码派生 | **scrypt**（n=2^14, r=8, p=1） | 内存硬化。本机实测约 190ms，是体验与破解成本的平衡点 |
| 每文件子密钥 | **HMAC-SHA256(主密钥, 路径)** | 一个文件被攻破不影响其他；不给攻击者判断两个文件内容相同的线索 |
| 块认证 | **路径 + 块序号进 AAD** | 密文块被调换、被搬到别的文件，解密都会失败 |

### 文件格式（二十年后还能解开）

每个 `.lfc` 文件 = **明文 JSON 头** + 若干 `nonce + 密文 + tag` 记录。

头部包含算法名、KDF 参数、原始路径、明文长度、源文件 SHA256。
**头部故意不加密**——二十年后没有这个程序，一个懂密码学的人也能照着它解开。

### 永远明文的文件（设计约束，不是遗漏）

| 文件 | 为什么必须明文 |
|---|---|
| `00-说明.md` | 否则没人知道这个档案是什么 |
| `01-授权/` | 否则没人知道谁有权使用它 |
| `90-审计/` | **锁操作本身要写日志**。加密它会导致「加密→写日志→新明文」永不收敛 |
| `密钥信封.json` | 解密所需的公开参数，不含密钥本身 |
| `加密清单.json` | 解锁索引 |
| `_meta.json` | 档案元数据 |

**代价要说清楚**：`90-审计/` 里的日志记录了操作时间和文件数，但不含消息内容和口令。
**它泄露的是"有哪些操作发生过"，不是"内容是什么"。**

### 三条不可违背的顺序

1. **先验证再删原文**：加密 → 用同一把钥匙解一遍验证 → 逐字节一致 → 才删明文。
   反过来做，中途失败就是永久丢数据。
2. **解锁默认保留密文**。删密文要显式加 `--remove-ciphertext`。
3. **换口令只重新包裹主密钥，不重新加密档案**。所以很快，也不会碰到数据。

## 为什么打破"零依赖"

项目原本零第三方依赖。加密是唯一一次破例，只引入 `cryptography`。

**理由**：加密不能自己写。密码学实现错了不会报错——它看起来能正常工作，
测试也过，但实际不安全。AES-GCM 的认证标签必须在使用明文前验证、
nonce 绝不能重用、错误消息不能泄露信息，这些都不是"能跑就行"的东西。

`cryptography` 底层是 OpenSSL，经过大量实战检验，有 Windows 预编译轮子
（不需要 MSVC）。这一条比"零依赖"的美感值钱。

## 当前状态

**已实现**
- 档案结构、说明文件、授权文件桩（含 12 类授权粒度 + 身后指令 + 密钥托管）
- 导入适配器：CSV / TSV / JSONL / JSON / HTML / 纯文本，自动编码探测
- 内容类型标注（7 类，带判定规则和置信度）
- 媒体文件登记（不解析，只登记哈希和路径）
- SQLite + FTS5 检索（中文按字符级索引，支持 1 字到多字查询）
- 人类可读呈现层（4 份清单）
- 审计日志
- **加密**：AES-256-GCM 分块加密、DPAPI + 口令双路密钥、密钥信封、
  加锁/解锁/校验/换口令/删 DPAPI 方式
- **101 个自检用例**（50 采集 + 51 加密）

**未实现（下一步）**
- 秘密共享的密钥托管（方案已确认倾向 A，代码未写）
- 桌面界面（pywebview）
