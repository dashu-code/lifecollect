# 档案标准 v0.1

> **状态**：草案，待评审
> **日期**：2026-10-15
> **适用范围**：第一代，Windows 优先
> **定位**：本文件定义"数字永生档案"的目录约定、元数据字段、授权文件格式与安全级别。它是采集器、归档器、导出器的共同接口。

---

## 0. 这个标准解决什么问题

现成标准已经存在，不要另立。**对接对象是 DLRS**（Digital Life Repository Standard，MIT，见 `DLRS核查备忘.md`）。

DLRS 已经定义了成熟的部分：
- `.life` 档案包的 JSON Schema（16 个 schema，287 个用例通过）
- 指针文件（pointer）模式：仓库只存指针，原始素材放外部存储
- 敏感度分级、同意模型、审计事件、撤回端点

**DLRS 缺失的部分正是本项目要做的那一块**：它假设材料已经被整理好了，没有任何从个人设备或社交平台提取素材的工具。

所以本标准的定位是：**定义"从原始素材到 DLRS 兼容档案"的中间层**，而不是重新定义档案格式。

---

## 1. 三层结构与权威性

| 层 | 存什么 | 权威性 |
|---|---|---|
| **原始层** | 导出的原始文件（聊天数据库、SILK 语音、原图、邮件原文） | **权威。永不修改、永不删除** |
| **索引层** | SQLite + FTS5 全文检索 | **可抛弃。损坏后能从原始层重建** |
| **呈现层** | 人类可读目录：清单、时间线、样本、授权声明 | **给人看的权威版本** |

**核心约束：权威性在文件上，不在数据库上。**

验收方式（场景 B）：用户的应用无法运行、且无人会写代码时，档案仍是完整可读的。

## 2. 目录约定

### 2.1 顶层结构

```
<档案根目录>/
├── 00-说明.md              # 给未来读者：这是什么、怎么读、谁能用
├── 01-授权/                # 授权与身后指令
├── 10-原始/                # 原始层，按来源分
├── 20-派生/                # 从原始层派生的可读文本
├── 30-索引/                # SQLite + FTS5（可重建）
├── 40-呈现/                # 人类可读清单、时间线、样本
└── 90-审计/                # 操作日志（append-only）
```

### 2.2 原始层内部

```
10-原始/
├── wechat/
│   ├── _meta.json          # 来源适配器、提取时间、工具版本、来源级别
│   ├── raw/                # 原始导出文件，按类型
│   ├── csv/                # 工具直接产出的 CSV
│   └── audio/              # 语音消息原始文件（SILK 等）
├── photos/
├── email/
├── documents/
└── manual/                 # 手工放入的材料
```

### 2.3 Windows 命名硬约束（实测得出）

档案目录名必须避开 Windows 限制，否则档案无法在其他机器上还原：

- **禁用字符**：`< > : " / \ | ? *`
- **保留名**（不可作为文件/目录名）：`CON PRN AUX NUL COM1-9 LPT1-9`
- **路径长度**：默认上限 260 字符。档案目录嵌套深，**必须主动处理**（见 §7）
- **结尾空格和点**：Windows 会静默去掉，导致路径不匹配

**因此：目录名只用中文、拉丁字母、数字、连字符。**

## 3. 元数据字段

每条材料记录以下字段。字段名用 snake_case，单位用 SI。

### 3.1 必备字段

| 字段 | 说明 |
|---|---|
| `record_id` | 唯一 ID |
| `source` | 来源：`wechat` / `photos` / `email` / `documents` / `manual` |
| `source_level` | **来源可信级别 1-4**（见 §4，降级链） |
| `captured_at` | 原始时间（消息时间戳，不是导入时间） |
| `imported_at` | 导入时间 |
| `kind` | 类型（见 §3.2） |
| `sha256` | 原始文件哈希 |
| `raw_path` | 相对档案根目录的原始文件路径 |
| `derived_path` | 派生文本路径（可为空） |
| `sensitivity` | `S0_PUBLIC` / `S1_INTERNAL` / `S2_CONFIDENTIAL` / `S3_BIOMETRIC` / `S4_IDENTITY` |

`sensitivity` 沿用 DLRS 的分级，不自造。

### 3.2 `kind` 取值（决定材料对下游的价值）

| kind | 含义 | 对下游的价值 |
|---|---|---|
| `chat_casual` | 闲聊、事务性（"收到""几点到"） | **低**——会稀释风格信号 |
| `chat_opinion` | 表达观点、判断、立场 | **高** |
| `chat_emotion` | 情绪表达、冲突、亲密对话 | **高** |
| `chat_media` | 语音、图片、视频消息 | **高**（音色来源） |
| `authored` | 自己撰写的：笔记、文章、邮件 | **最高** |
| `third_party` | 别人写给他的 | **零**（不是他的语料） |

**这一列是本标准最有价值的部分。** 下游工具（微调、克隆）需要它，而原始素材里没有这个信息。

### 3.3 `third_party_present` 标志

一条材料里如果包含第三方的私人内容（聊天记录必然包含），必须标记。

理由：这是《个人信息保护法》的实际约束，也是"上传到云端前必须脱敏"的依据。**不标就无法做脱敏，也就无法安全导出。**

## 4. 来源可信级别（降级链）

同一个来源可能有多种提取方式，可信度不同。**每条记录必须标注它来自哪一级。**

| 级别 | 方式 | 能采到 | 触发条件 | `source_level` |
|---|---|---|---|---|
| 1 | 直接读取数据库（如 PC 端解密） | 文字 + 类型 + 时间 + 可提取语音 | 默认路径 | `1` |
| 2 | 手机端整体备份 / 直接导出 | 同上，视机型权限 | 级别 1 失败 | `2` |
| 3 | 截图 + OCR | **仅文字**，无语音、时间精度差 | 前两级都不通 | `3` |
| 4 | 手工录入 | 视录入者 | 兜底 | `4` |

**要求**：下游工具应当区别对待不同级别的材料。**这不是可选的元数据，是材料可信度的一部分。**

---

## 5. 安全级别（用户可选）

**用户在选择时看到的必须是"挡什么"和"不挡什么"两栏，不是"低/中/高"。**

| 级别 | 密钥保护 | 挡什么 | **不挡什么**（必须原文显示给用户） |
|---|---|---|---|
| `basic` | 不加密，或仅混淆 | 顺手翻看、误删 | 拿到文件的人。**等于没有加密保护** |
| `standard`（默认） | 密钥由 Windows DPAPI 保护 | 磁盘被单独拿走 | 能接触已解锁机器的人；运行中的进程 |
| `paranoid` | 密钥由用户主密码派生（Argon2id），可配秘密共享 | 上述 + 无密钥者离线暴力破解 | **密钥丢失即永久不可读，没有任何人（包括作者）能恢复** |

### 5.1 三条工程约束

1. **`security_level` 是档案内持久化字段**，不是应用设置。档案在机器间移动时必须自带级别。
2. **禁止任意原地升降级。** 从 `standard` 升到 `paranoid` 意味着换密钥，**必须先验证新密钥可解密再销毁旧密钥**。降级同理。
3. **所有级别都是已实现的功能，不是占位。** 界面上不提供未实现的选项。

### 5.2 级别对档案格式的影响

`basic` 与 `paranoid` 的档案**内部结构不同**（前者明文，后者加密包）。因此：

- 说明文件 `00-说明.md` **永远明文**——否则无人能知道这是什么
- 授权文件 `01-授权/` **明文**（不含敏感内容）
- 可读派生文本与原始层受级别保护

## 6. 授权文件格式

### 6.1 结构

```
01-授权/
├── 授权声明.md            # 人类可读
├── 授权声明.json          # 机器可读，同内容
├── 身后指令.md            # 本人去世后谁能决定什么
└── 密钥托管.json          # 密钥恢复方式（见 §6.3）
```

### 6.2 授权声明必须覆盖的粒度

沿用 DLRS `standards/dlrs/v0.2/rights-and-consent.md` 列出的 12 类粒度，逐项标注允许 / 禁止：

存储、结构化处理、文本人格构建、语音克隆、视频/头像克隆、3D avatar 构建、模型微调、公开索引、商业使用、跨境处理、研究使用、纪念化运行。

**每项三态**：`allow` / `deny` / `unset`（未设定）。`unset` 一律按 `deny` 处理。

### 6.3 密钥托管

用户在安装时选择，且可随时改。**倾向的默认是 A**：

| 方案 | 机制 | 事实后果 |
|---|---|---|
| **A**（倾向默认） | Shamir 秘密共享 + 制度托管（律所/公证处持份额，遗嘱指定执行人发起） | 单一受托方背叛无效；需要凑够份额 |
| **B** | 商业密码管理器的紧急访问 | 省事；**依赖第三方公司存续** |
| **C** | 单一受托人 | 简单；单一主体可背叛，且依赖该人 |

**已评估并否掉的方案**：用"人生经历选择题"作为密钥恢复手段。

否掉理由：答案存在于被保护的档案内部（读完档案即可答对）；且把密钥安全降到"认识他的人"的水平；且正确率阈值无法同时满足"家人答得对"和"外人答不对"。**"就一两次机会"不构成保护**——攻击者会直接拿走加密文件离线尝试，不会使用你的界面。

### 6.4 标注义务

授权文件必须包含一条**随档案传递的义务声明**：

> 使用本档案生成的一切内容，必须显著标明为 AI 合成内容。

理由是法规层面的深度合成标识要求。这不是建议，是使用者必须知道的约束。

## 7. Windows 平台约束（实测记录）

第一代只做 Windows。以下为必须正面处理的事项：

| 事项 | 状态 | 处理方式 |
|---|---|---|
| **长路径（>260 字符）** | 未验证 | 档案嵌套深，需实测并可能启用长路径支持 |
| **文本编码** | **已实测踩到** | 中文 Windows 默认 GBK。**所有文本 IO 必须显式 `encoding="utf-8"`** |
| **控制台输出编码** | 已实测踩到 | 读子进程输出需显式 UTF-8，否则 `UnicodeDecodeError` |
| **路径分隔符** | 已实测踩到（DLRS 案例） | **内部一律用正斜杠或 `pathlib`，禁止字符串拼接路径** |
| **WebView2 运行时** | Win11 预装 | Win10 需要 Evergreen 引导 |
| **杀毒软件拦截** | 已确认为高风险 | 采集工具读进程内存会被拦；必须有降级路径与用户提示 |
| **保留文件名** | 已知 | 目录命名规则见 §2.3 |

**平台相关代码隔离在单一模块内**，Windows 特有行为集中于此，不散落在业务逻辑里。

## 8. 验收场景

标准是否正确，用四个场景检验：

**场景 A（采集，今天）**：非技术用户装好应用，导入微信记录 + 语音 + 照片，标注完成，导出一套档案。**全程不联网。**

**场景 B（十年后，无工具）**：家人拿到文件夹，没有这个应用、无人会写代码。能知道这是什么、能读内容、能交给下游工具。

**场景 C（灾难恢复）**：家人拿到一份备份，**没有本人、没有这个应用**，能打开。

**场景 D（继承验证）**：本人去世后，家人找到托管方，按指示凑够份额还原密钥，**在不知道本人任何私事的前提下**打开档案。

**场景 B、C、D 是真正的验收标准。场景 A 只是过程。**
